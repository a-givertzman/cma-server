# Functions of Task service

## Правила написания функций

Любая **«нечистая»** (impure) функция, которая черпает данные извне графа (системное время, генератор случайных чисел, чтение из внешней БД), **всегда возвращает `Flow::New`**, если ее значение физически изменилось с прошлого вызова.
Это заставит все зависимые от нее узлы с состоянием (счетчики, интеграторы) честно отработать свои вычисления.

### Разделение входов функций (Как заражать `Flow`)

- **Триггеры/Данные (Input) - Участвуют в `Flow`**

    Это пульс системы. Изменение этих данных является причиной для расчетов. Они **обязаны заражать `Flow`**.
    - input
    - enable
    - reset
    - trigger
    - gate
    - pass

- **Параметры (Config) - Не участвуют в `Flow`:**

    Это вспомогательные данные. Тот факт, что уставка или начальное значение обновились (или были прочитаны в первый раз), сам по себе не должен провоцировать ложное срабатывание счетчика. Счетчик тикает только от фронта на входе.
    - initial
    - threshold
    - factor
    - delay
    - coefficients
    - piecewise

### Поведение функций (Taint Tracking)

1. **Воды (FnInput):**
* Возвращают `New`, только если `updated_at_cycle == current_cycle`. Иначе `Old`.
* *Отвечают за точку отсчета.*

2. **Генераторы (FnTimer, FnRandom):**
* Возвращают `New`, если сгенерированное значение отличается от прошлого (или просто всегда возвращают `New`, что проще и надежнее).
* *Выступают спонтанными источниками изменений.*

3. **Чистая математика (FnAdd, FnMath):**
* Возвращают `New`, если **хотя бы один** аргумент имеет статус `New`. Иначе `Old`.
* *Математика сама по себе не создает событий, она только проводит их.*

4. **Узлы с состоянием (FnCount, FnIntegrator, FnRisingEdge):**
* Анализируют аргументы. Если пришел `New` (от входа или таймера) — мутируют свой внутренний стейт (прибавляют счетчик, вычисляют интеграл). Возвращают `New`.
* Если все аргументы `Old` — ничего не считают, просто отдают свой старый кэш со статусом `Old`.

5. **Обертка (FnEvalOnce):**
* Честно кэширует статус `Flow` и значение `Point` для текущего вычислительного цикла. Спасает от повторных вычислений чистой математики, если ее дергают из разных веток графа в один цикл несколько раз.

# Архитектурный стандарт графа вычислений

## Основные правила

### 0. Обход ловушки ленивых вычислений (short-circuit evaluation trap)

Что бы не пропустить такт и не заморозить паралельные ветки вычисления необходимо сначала выполнить  Fetch всех входов, а потом раскрывать результаты

* **Фаза Fetch** (Безусловный опрос всех входов)
let input = self.input.out();
let threshold = self.threshold.out();
let factor = self.factor.as_mut().map(|f| f.out());

* **Фаза Check** (Проверка Taint Tracking)
let mut flow = FlowContext::new();
let Some(input) = flow.map(input)? else { return Ok(None) };
let Some(threshold) = flow.ignore(threshold)? else { return Ok(None) };
let Some(threshold) = match flow.ignore(threshold)? else { return Ok(None) };

Или что бы не потерять валидное значение например по ветке flow.is_old() необходимо размещать все вычислительные операции особенно с возможной неудачей там где они фактически нужны. Что бы не тратить CPU на их вычисление и не вернуть ошибку вместо flow.wlap_old(last).
let value = match input.type_() {
    PointType::Bool | PointType::Int | PointType::Real | PointType::Double => input.to_double().as_double().value,
    _ => return Err(concat_string!(self.id, ".out | Invalid input type '", input.type_().to_string(), "'")),
};


### 1. Кровеносная система: `FnFlow`

`FnFlow` — это гибрид. Он несет физическое значение (`Point`) для математики и триггер для управления состоянием системы (Taint Tracking).

* **`Ok(New)`**: Данные обновились физически (значение или статус качества). Это приказ графу: «Выполнить расчет и записать в базу!».
* **`Ok(Old)`**: Данные валидны, но не изменились с прошлого такта. Это валидные значения для формулы, которую можно вычислить если есть другие значения New и не считать , если все Old, вернуть закэшированное значение прошлого такта.
* **`Ok(None)`**: Сигнала нет (обрыв связи, остановка). Прерывает любые вычисления по ветке.
* **`Err`**: Ошибка в вычислениях, NAN. Прерывает любые вычисления по ветке.

> Примечание! `NAN` на входе функций считаем невалидным значение, возвращаем `Err`
### 2. Стражи границ: `FnChange` и `FnEnable`

Эти декораторы инкапсулируют логику управления потоком, освобождая математические узлы от лишней ответственности (SRP).

* **`FnChange` (Нормализатор генерации):** Жесткий шлюз. Перехватывает на входе как `New`, так и ленивые `Old`. Сравнивает физическое значение и статус со своим внутренним кэшем. Изменилось — принудительно рождает `New`. Не изменилось — принудительно гасит в `Old`. Гарантирует абсолютную защиту от спама дубликатами. Должен оборачивать все входы грязных функций.
* **`FnEnable` (Управляемый рубильник):** Оборачивает функции, которые имеют вход `enable`. Режет или пропускает поток по логическому сигналу.
    * *Cold*: Выдает `None` и сбрасывает зависимые узлы (аппаратная остановка).
    * *Warm*: Понижает `New` до `Old`, удерживая последнее валидное значение (мягкая пауза).

### 3. Золотые правила изоляции стейта (Pull-model)

Сборщик графа (`FnBuilder`) должен оставаться простым механизмом сборки труб, не знающим, какая вода по ним течет. Объекты обязаны защищать себя сами.

* **Чистые функции (Stateless):** Например, `FnAdd`, `FnRound`. Не имеют кэша `last_val`. Оставляем их «голыми». Они принимают сырые данные, быстро считают и транслируют статус входа дальше. Экономит RAM и такты CPU на проверках кэша.
* **Грязные функции (Stateful):** Например, `FnAverage`, `FnCount`. Ломаются от паразитных `New` (чистого шума). Обязаны защищать свои границы. Внутри своего конструктора `new()` функция сама оборачивает переданные ей сырые входы в `FnChange`. Это дает независимость потоков при множественных подписках.
* **FnEvalOnce (корневая функция):** Стоит в корне каждой вычислительно ноды. Блокирует повторный пересчет в пределах одного цикла.

### 4. Архитектурный прагматизм и чистые функции

* **Инкапсуляция важнее наносекунд:** Отказ от `Rc<RefCell>` и переход на единый контекст стейта признаны избыточными. В реалиях ОС общего назначения и цикла в 1 мс затраты на умные указатели ничтожны. Мы сохраняем классическое ООП: каждый узел остается изолированным черным ящиком, который сам владеет своим состоянием.
* **Разгрузка метода `out`:** Вычислительные и агрегирующие узлы больше не занимаются маршрутизацией и фильтрацией мусора. Вся логика управления потоком (обработка пауз, отсечение дубликатов) жестко вынесена в декораторы `FnChange` и `FnEnable`. Метод `out` внутри функций обязан быть максимально лаконичным: запросить гарантированно чистые данные, выполнить свою логику и вернуть результат.

Проверь эти правила глядя в текущий исходник, он в процессе рефакторинга, но архитектура там видна.

## Архитектура Stateful-узлов (Грязных функций)

Грязные функции в SCADA-графе делятся на два принципиально разных класса. Для каждого из них действуют свои правила обработки потока (`FnFlow`).

### 1. Событийные узлы (Event-Driven)

**Примеры:** `FnCount`, `FnMax`, триггеры, детекторы фронтов.

* **Физика:** Реагируют исключительно на факт изменения входного сигнала.
* **Правило `out()`:** Математика выполняется только если `flow.is_new() == true` (или сработал `force_recalc` от сигнала сброса). Если на входе абсолютная тишина (`Old`), узел спит и мгновенно возвращает кэшированное значение через `flow.wrap_old(cache)`. Никаких лишних тактов процессора.

### 2. Временные интеграторы (Time-Driven)

**Примеры:** `FnAverage`, `FnAcc`, ПИД-регуляторы, таймеры задержки.

* **Физика:** Реагируют на течение времени. Каждый вызов графа — это $dt$.
* **Правило `out()`:** Значение читается и математика выполняется **в каждом такте**, независимо от того, пришел сигнал как `New` или как `Old`.
* **Парадокс Интегратора:** Интегратор имеет законное право возвращать `New`, даже если на всех его входах висит `Old`. Пока его внутреннее состояние (например, накопленная сумма или выход ПИД-регулятора) стремится к уставке, узел выступает как активный генератор изменений. Он перейдет в `Old` только тогда, когда его выходное значение перестанет меняться.

### 3. Гигиена входов и SRP (Границы декораторов)

Никогда не смешивай бизнес-логику узла с механизмами защиты графа. За это отвечают специализированные декораторы, и стоять они должны на своих местах:

* **Внутренний страж (`FnChange`) — Защита от спама:**
Применяется **строго внутри** метода `new()` грязной функции для обертывания сырых входов (`input: FnChange::new(input)`).
*Задача:* Защитить Taint Tracking внутри функции. `FnChange` не блокирует поток данных, он лишь красит шумовые дубликаты из `New` в `Old`. Функция сама следит за гигиеной своих аргументов.
* **Внешний рубильник (`FnEnable`) — Управление жизненным циклом:**
Применяется **строго снаружи** (чаще всего билдером). Сама математическая функция никогда не должна знать о существовании входа `en`.
*Задача:* Отсечь узел от графа. Функция пишет свой код так, будто работает всегда. Декоратор берет на себя заморозку значения в `Old` (режим Warm) или проброс `None` (режим Cold).

### 4. Правила Taint Tracking (FlowContext)

При написании метода `out()` любой грязной функции:

1. **Все** входы, способные повлиять на результат графа (рабочий сигнал, триггер сброса, границы лимитов), обязаны проходить через `flow.map()`. Чтение `input.out()?` в обход контекста — это критическая архитектурная ошибка, которая сделает граф «глухим» к событиям.
2. Флаг `flow.is_new()` внутри узла становится `true`, если **хотя бы один** из входов, пропущенных через `map()`, принес статус `New`.
3. Итоговое значение узла отдается не ручным конструированием `FnFlow`, а методами контекста: `flow.wrap_new(point)` (для принудительной генерации события) или `flow.wrap(point)` (контекст сам решит, отдать `New` или `Old` в зависимости от собранной «грязи» со входов).

## Data Path против Control Path

В графе вычислений есть два типа сигналов:

1. **Информационный тракт (Data Path):** Это наш `input`. Любое его изменение — это новые физические данные. Мы **обязаны** пропускать его через `flow.map()`.
2. **Управляющий тракт (Control Path):** Это `reset`, `enable`, `limits`. Их задача — управлять поведением узла, а не нести данные.

**Что будет, если пропустить `reset` через `flow.map()`?**
Представь: сигнал `reset` переходит из `true` в `false` (задний фронт). Контекст `flow` радостно помечает себя как `New`, потому что сигнал изменился. В итоге узел `FnAverage` решает, что у него новые данные, и выбрасывает в сеть событие `FnFlow::New(average)`, хотя математически ничего не поменялось (накопитель не сброшен, новый `input` не приходил). Это ложное срабатывание, которое породит волну бессмысленных пересчетов по всему графу.

**Твое решение в коде — эталонное.**
Ты интуитивно нашел самый правильный архитектурный паттерн:

* Читаем управляющий сигнал «сырым», без `flow.map()`.
* Ищем нужный триггер (в нашем случае `Edge::Rising`).
* Если триггер сработал, мы физически очищаем память узла и поднимаем флаг (у тебя это `force_recalc`, я переименую в `state_mutated` для академичности).
* В конце узла, если флаг поднят, мы принудительно отдаем `FnFlow::New`, так как наше состояние изменилось изнутри.

Этот подход полностью изолирует грязные фронты управляющих сигналов от потока данных, но гарантированно уведомляет граф, когда узел реально изменил свое математическое состояние.
Это фундаментальные правила, которые мы вывели на основе отладки `FnAverage`, `FnMax` и `FnEnable`.
